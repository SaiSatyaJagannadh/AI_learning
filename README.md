# Log Agent Harness: A Tutorial

This repository contains a minimal agent harness for debugging production logs. It's designed to teach you how an agent harness works by favoring clarity over cleverness.

## What is an Agent Harness?

An agent harness is the scaffolding that turns a language model into an agent capable of interacting with the world via tools. The harness manages the conversation loop, executes tools, and provides safety mechanisms (brakes).

Unlike frameworks that hide the loop, this implementation makes the `while stop_reason == "tool_use"` loop explicit so you can see every moving part.

## The Agent Loop (in 9 lines)

Here's the core of `logagent/harness.py`:

```python
while self.turn_count < self.max_turns:
    completion = self.llm_client.complete(
        messages=self.messages,
        max_tokens=self.max_output_tokens - self.output_token_count,
    )
    self.messages.append({"role": "assistant", "content": completion["content"]})
    
    if completion["stop_reason"] == "tool_use":
        tool_results = self._execute_tool_calls(completion["content"])
        self.messages.append({"role": "user", "content": tool_results})
    elif completion["stop_reason"] == "pause_turn":
        break
    else:
        break
```

This loop:
1. Gets a completion from the LLM
2. Appends the assistant's content **verbatim** (so thinking blocks survive)
3. If the LLM wants to use tools, executes them and appends results as a single user message
4. Handles pause_turn and stop conditions
5. Applies brakes on turns, tool calls, and output tokens

## Walkthrough: Running the Agent

First, generate sample logs:

```bash
python scripts/generate_sample_logs.py
```

This creates four log files in `./logs` describing a cascading failure:
- `deploy.log`: shows a config change (DB_POOL_SIZE increased)
- `database.log`: shows connection refusals due to the change
- `service.log`: shows timeouts waiting for the database
- `gateway.log`: shows 502 errors from the service being down

Now run the agent with a mock client (no API key needed):

```bash
python cli.py --initial-prompt "Investigate the 502 errors in the gateway logs" --mock
```

You'll see the transcript showing each turn, tool calls, and results. The agent will:
1. List logs to see what's available
2. Search for "502" in the gateway logs
3. Read relevant lines around those errors
4. Check database logs for connection issues
5. Correlate events across logs using the timeline tool
6. Conclude that a deploy increased the DB pool size, overwhelming the database

## Running with NVIDIA API (Production)

To run the agent with a real LLM (NVIDIA's models via their API):

**1. Install dependencies:**
```bash
pip install -r requirements.txt
```

**2. Set up your API key:**

Create a `.env` file (copy from `.env.example`):
```bash
cp .env.example .env
```

Edit `.env` and add your NVIDIA API key:
```
NVIDIA_API_KEY=nvapi-your-actual-key-here
NVIDIA_MODEL=meta/llama-3.1-405b-instruct
```

**3. Run the agent:**
```bash
python cli.py --initial-prompt "Investigate the 502 errors in the gateway logs" --nvidia
```

The agent will now use NVIDIA's API with the Llama 3.1 405B model (or whatever model you configured) to actually reason through the logs and use tools intelligently.

**Available NVIDIA models:**
- `meta/llama-3.1-405b-instruct` (default, most capable)
- `meta/llama-3.1-70b-instruct` (faster, cheaper)
- `nvidia/nemotron-4-340b-instruct` (NVIDIA's own model)

You can also pass the API key directly via command line:
```bash
python cli.py --initial-prompt "Find the root cause" --nvidia --api-key nvapi-your-key
```

## What Turns a Loop into a Harness?

The loop above is necessary but not sufficient. A harness adds:

### 1. Brakes (Safety Limits)
- `max_turns`: prevents infinite loops
- `max_tool_calls`: caps total tool invocations
- `max_output_tokens`: limits tokens generated by the LLM
These prevent runaway costs and keep the agent focused.

### 2. Tool Safety
- Each tool can be marked `dangerous` (e.g., file deletion)
- Dangerous tools require approval via an `approve()` hook
- If refused, the tool returns an error result (not an exception) so the LLM learns

### 3. Verbose Transcript
- Every turn, tool call with arguments, and result preview is printed
- This is essential for debugging agent behavior
- Without it, you're flying blind

### 4. Tool Result Integrity
- Tools **must** clamp output to a character budget and say what they held back
  (e.g., "558 matches, showing 12, 546 not shown — narrow your pattern")
  Silent truncation makes the LLM reason over incomplete data.
- Tool failures return results with `is_error: true`, **never** exceptions
- Error messages tell the LLM what went wrong **and** what to try next

### 5. Path Safety
- Every file path is resolved and confined to a log root
- Prevents path traversal attacks

### 6. Purpose-Built Tools
The five tools are designed for log debugging:
- `list_logs`: discover what logs exist
- `search_logs`: regex search with context (capped output)
- `read_log`: paginated line-range reading (no "read whole file")
- `log_stats`: severity counts and time-series histogram
- `timeline`: merge multiple logs chronologically around a timestamp

## Why Tool Design Beats Tool Count

This harness has only five tools, but they're powerful because:
- They compute for the LLM: the `timeline` tool does the hard work of merging and sorting logs by timestamp
- They prevent silent failures: clamped output with honesty about truncation
- They're composable: use `search_logs` to find interesting times, then `timeline` to see the full picture
- They're safe: no tool can read arbitrary files or execute commands

Adding more tools often creates overlap and confusion. Five well-designed tools beat twenty poorly designed ones.

## When to Use the SDK's Tool Runner

The Anthropic Python SDK provides `ToolRunner` and `agentic_loop` utilities. Consider using them when:
- You need production-grade reliability (retries, better error handling)
- You want to use the latest model features (like built-in tool choice)
- You're building a complex agent with many tools and need conversation summarization
- You prefer not to manage the loop yourself

However, avoid them when:
- You're learning how agents work (like now)
- You need full control over the loop (e.g., custom brakes, transcript)
- You want to avoid extra dependencies
- You're optimizing for clarity over convenience

This harness is intentionally minimal to teach the underlying concepts. Once you understand it, you'll be better equipped to use (or extend) framework solutions.

## Files Overview

- `logagent/harness.py`: the agent loop with brakes and transcript
- `logagent/tools.py`: tool registry and execution plumbing
- `logagent/logtools.py`: the five log tools (with output clamping and safety)
- `logagent/llm.py`: LLM client abstraction (MockClient for testing, ClaudeClient stub)
- `logagent/transcript.py`: prints every turn, tool call, and result preview
- `cli.py`: command line interface
- `scripts/generate_sample_logs.py`: generates the sample log data
- `tests/test_harness.py`: unit tests for the harness
